## Modular Crates Structure

Isolock is organized as a Cargo workspace with four domain library crates and one CLI binary:

```text
crates/
├── isolock-core/   # Shared primitives, versioning, semver, and registry taxonomy
├── isolock-cas/    # Content Addressable Storage (CAS) and SHA-256 validation
├── isolock-plan/   # Airlock execution plan, lockfile diffs, and drift guards
├── isolock-proxy/  # Local HTTP interceptor proxy and fail-closed routing
└── isolock/        # User-facing CLI application binary
```

## Security Invariants

1. **No Upstream Proxy Fallback**: In `Ci` and `LocalAirlock` modes, uncached proxy requests fail closed. Proxy configuration is not an OS/network sandbox for arbitrary child programs.
2. **Deterministic Digests**: Every artifact stored in CAS is verified against lowercase 64-hex SHA-256 hashes.
3. **Locked Input Verification**: Profile checks compare reviewed configuration and input digests. Legacy plan checks compare an expected JSON plan against local CAS bytes; they do not resolve project dependencies.

## Command-line boundary

`main` delegates to one non-interactive `clifacet::App::for_cli` pipeline. The root controller
in `cli` is declared with `#[clifacet::app]`; its commands are methods in a
`#[clifacet::commands]` implementation. Clifacet generates the command enum, collection,
validation, dispatch, and lifecycle wiring, without application-authored request enums
or per-command `Command`/`Handler` implementations.

`#[clifacet::group]` declares argument groups that retain command metadata such as the
`bootstrap` alias, application version label, and opaque `exec` argument tail. The nested
configuration controller uses `#[clifacet::group(commands)]` and
`#[clifacet::commands(group)]`, with parsed overrides supplied through context extraction.
Profile and proxy operations receive typed values and never reparse process arguments.
The plan method selects profile planning or the legacy airlock check from those values
and the presence of project configuration.

Usage errors exit with status 2 and execution failures with status 1. Help and version
requests exit successfully before loading configuration or creating application state.
A small output adapter preserves a completed child's exact exit status without adding
output or overriding a clifacet runner failure.

## Reviewed ingestion and storage publication

The declarative `ingest` and `push` groups use the same CLI/configuration boundary.
Manifest validation, local/explicit-connected staging, publication assembly, and isolated
Git plumbing have separate modules. Original bytes enter the configured CAS only after
selected-batch validation. Immutable ingestion objects also register conservative shared-CAS
GC roots.

Publication appends a non-force `chore(deps)` storage commit using a private index, without
checking out storage or staging producer files. Profile publication reuses the verified
export and checks originals against the earlier locked payload commit. Live-tree limits
fail closed; automatic epoch rollover and registry solving are not implemented. See
[reviewed ingestion and publication](./ingestion.mdx) for the exact schema and boundaries.

## Execution and proxy ownership

The CLI resolves configuration once at its Figment boundary. `proxy_cli` owns proxy
orchestration; `ExecutionSession` owns proxy/Pixi-file lifetime; Cargo and Pixi generators,
child-environment contributions, input loading, and exit mapping have separate modules.
Core planning, CAS, and proxy crates never read operational process configuration.

`default_adapters` owns registry composition, while the server owns loopback admission and
routing. Separate request, response, and resource modules implement HTTP parsing, closed
response classification/transforms, absolute socket deadlines, and bounded worker accounting.
See [proxy execution and limits](./proxy.mdx) and the [Rust quality policy](./quality.mdx).
