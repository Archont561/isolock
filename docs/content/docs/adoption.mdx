## What adoption actually requires

Isolock does not resolve versions, discover transitive dependencies, or turn an unreviewed
download into a trusted pin. Every artifact arrives through an explicit reviewed pin, and
publication is a separate action from review.

That shapes adoption: a maintainer commits **configuration and pins**, publishes **bytes**
to a storage branch, and a consumer restores from those bytes without contacting the
original sources.

## The files a consumer commits

`isolock init` writes two of them. A complete adopted project commits:

| Path | Source | Commit? |
|---|---|---|
| `isolock.toml` | generated by `isolock init`, then reviewed | yes |
| `isolock.ingest.json` | generated by `isolock init`, then reviewed | yes |
| Lockfiles (`Cargo.lock`, `pixi.lock`, `requirements.lock`, `package-lock.json`) | your package manager | yes, when the profile is lock-driven |
| `.isolock/plans/*.lock` | `isolock plan` | yes, so CI can verify drift |
| `.isolock/seeds/`, `.isolock/bootstrap.sh` | `isolock seed-manifest` | yes, if you use the shell bootstrap |
| `.isolock/cas/`, `.isolock/profiles/`, `.isolock/transport/` | generated | **no** |
| Original archives (`originals/`) | you downloaded them for review | **no** |

The rule is the one the ingestion guide states: reviewed text stays with code, payloads stay
out of code branches. A conventional `.gitignore` entry is:

```sh
.isolock/cas/
.isolock/profiles/
.isolock/transport/
originals/
```

CAS contents are reproducible from published storage, so committing them duplicates storage
and defeats the two-tier split.

## The order that produces a published profile

Each step is explicit, and the order matters. `ingest` verifies bytes into the CAS, `plan`
locks the reviewed graph, and only then can `push` publish a profile.

```sh
isolock init --profile dev --platform linux-64     # scaffold, then review the pins
# edit isolock.toml and isolock.ingest.json: every digest is now a real reviewed value
isolock config check
isolock ingest --manifest isolock.ingest.json --artifacts originals
isolock push --manifest isolock.ingest.json
isolock plan --profile dev --platform linux-64
isolock push --profile dev --platform linux-64
```

With `storage.transport = "git"` the two `push` calls publish different things: the first
publishes the artifact objects, the second publishes the locked profile manifest and its
alias. The second requires the first, because the profile must reference a commit that
already contains every reachable original.

Real output from a scratch project with a local bare remote:

```console
$ isolock ingest --manifest isolock.ingest.json --artifacts originals
Verified 1 reviewed artifact(s) in CAS; publication requires isolock push

$ isolock push --manifest isolock.ingest.json
Published eebdf79e673bc13ea3bb6cbe0ce787be99fa8105 to refs/heads/isolock/v1

$ isolock plan --profile dev --platform linux-64
isolock transport: Git fallback fetches a broader storage snapshot; profile selection is local, not blob-selective transfer
Profile dev/linux-64: 6f00b0bd4e2e3d2261e191f801198b4a5a4aec14005de7f9d6fda361742c6090
plan: .isolock/plans/dev-linux-64.lock

$ isolock push --profile dev --platform linux-64
Published 4378f92d5425a4ed2e538b79b2e1d4dd2b636ee9 to refs/heads/isolock/v1
```

The "broader storage snapshot" line is not a warning about correctness. Git transport is not
blob-selective: it fetches a snapshot and then selects the reviewed closure locally. Only the
selected closure enters the consumer CAS.

## Storage branch setup

`push` writes a Git ref, by default `isolock/v1`, into a repository named by
`storage.source`. Nothing requires checking that branch out in the producer's working tree.

```toml
[storage]
cas-dir = ".isolock/cas"
transport = "git"
source = "git@github.com:example/repo-storage.git"
reference = "isolock/v1"
```

`push` needs a working Git repository with an author identity and a resolvable remote. Two
failures name exactly what is missing rather than guessing:

```console
$ isolock push --manifest isolock.ingest.json
isolock: Git repository discovery failed; check repository access, author configuration, and storage history

$ git init --quiet && git remote add origin ../storage.git
$ isolock push --manifest isolock.ingest.json
Published eebdf79e673bc13ea3bb6cbe0ce787be99fa8105 to refs/heads/isolock/v1
```

A dedicated storage repository is the recommended shape: it keeps payload history out of the
code repository's clone size, and the two refs then have independent retention.

## Offline consumer restore

A consumer commits `isolock.toml` and receives the published manifest digest out of band, for
example from the publish log or a release note. Then:

```console
$ isolock fetch --profile dev --platform linux-64 --manifest 6f00b0bd4e2e3d2261e191f801198b4a5a4aec14005de7f9d6fda361742c6090
isolock transport: Git fallback fetches a broader storage snapshot; profile selection is local, not blob-selective transfer
Fetched 1 selected blob(s); unrelated profiles were not copied into CAS
Profile dev/linux-64: selected closure is verified in CAS

$ isolock sync --profile dev --platform linux-64 --locked --offline
Profile dev/linux-64 ready: .isolock/profiles/dev/linux-64/6f00b0bd4e2e3d2261e191f801198b4a5a4aec14005de7f9d6fda361742c6090
Activate: . .isolock/activate/dev-linux-64

$ . .isolock/activate/dev-linux-64 && isolock --version
isolock 0.1.0
```

This output was captured after deleting the storage remote and the original archives, so the
restored prefix demonstrably does not depend on either. `--locked` refuses to replan, and
`--offline` refuses to transfer, which is the property worth asserting in CI: the profile runs
from bytes alone.

For a package-manager workflow inside that profile, `cargo add` and `pixi add` resolve from
the reviewed snapshot; see [the proxy guide](./proxy.mdx#package-managers-resolve-from-the-reviewed-snapshot).

## Generated workflow or documented template

**Documented, not generated.** The reasoning is that the workflows carry almost no per-repo
content. The publish job is a restore plus `isolock ingest`/`push` with a manifest path and a
registry name; the PR guard verifies a published snapshot and skips when no storage ref
exists. A renderer would emit a near-identical file for every repository, and the only
varying values are already `workflow_dispatch` inputs.

Copy [`isolock.yml`](https://github.com/Archont561/isolock/blob/main/.github/workflows/isolock.yml)
and review it. Two properties are worth keeping when you adapt it:

- Publication is `workflow_dispatch` only, never a pull-request trigger. A pull request may
  verify a published snapshot; it may never publish.
- Package selections arrive as literal argument entries with an option separator, never
  interpolated into a shell string.

If per-repo variance grows, a generator becomes worthwhile. It does not yet.

## What still needs hand authoring

`isolock init` ships a scaffold, not an automated setup. Still manual:

- **Every pin except the seed.** `init` writes one truthful pin, the running executable's
  own digest at an absolute `file://` path. That is machine-local: replace it with a real
  provenance URL before anyone else can `sync`. All artifact pins are yours to review.
- **The reviewed manifest.** `init` writes `{"schema-version": 1, "artifacts": []}`. An empty
  manifest is deliberate; a digest names bytes you hold, so a generated one would be a
  placeholder that validation rejects.
- **Lockfiles.** Isolock never writes `Cargo.lock`, `pixi.lock`, or equivalents. Your package
  manager produces them and you commit them.
- **`bootstrap.sh` and the seed manifest.** `seed-manifest` derives these from a locked plan;
  `init` does not emit them.
- **Storage repository and Git identity.** Provisioning the remote is yours. `push` reports a
  discovery failure rather than creating one implicitly.
- **CI workflow choice.** Documented as a template to copy and review, per the section above.

## Keeping the reviewed boundary visible

Two rules hold for everything on this page:

1. **No template resolves an artifact.** `init` writes an empty manifest; the publish
   workflow consumes pins a human already reviewed; no step discovers a version or a
   transitive dependency.
2. **A placeholder cannot pass.** A zero digest fails validation with the artifact named, and
   a digest whose bytes are absent fails `ingest` with `reviewed original SHA-256 mismatch`:
   ```console
   $ isolock ingest --manifest isolock.ingest.json --artifacts originals
   isolock: reviewed original SHA-256 mismatch
   ```

When adapting this guide, if a step would make Isolock choose a version, it does not belong
in an Isolock workflow.
