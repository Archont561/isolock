## Blocking checks

Use the restored, locked developer sandbox. The standard command is the same in local
validation and CI:

```sh
pixi run --as-is --offline cargo fmt --check
pixi run --as-is --offline cargo clippy --workspace --all-targets --offline -- -D warnings
pixi run --as-is --offline cargo nextest run --workspace --offline
pixi run --as-is --offline cargo test --workspace --offline
pixi run --as-is --offline cargo deny --offline check bans licenses sources
```

`Cargo.toml` selects individual lints rather than enabling `clippy::pedantic`,
`clippy::restriction`, or `clippy::cargo` wholesale.

- Production `unwrap()`, `expect()`, `dbg!`, `todo!`, and `unimplemented!` are denied.
- `format_push_string`, `map_unwrap_or`, `filter_map_next`, and `unused_self` prevent
  avoidable allocations and unused helper receivers.
- `cast_possible_truncation` and `large_stack_arrays` guard portability and worker stacks.
  CAS sharding uses a 64 KiB **heap** buffer, checked read lengths, and checked byte counters.
  Boundary tests include 64 KiB minus/exact/plus one, the shard ceiling, `u32::MAX`,
  `usize::MAX`, and `u64::MAX` without allocating huge artifacts for integer tests.
- Public fallible library APIs document `# Errors`; `missing_errors_doc` blocks omissions.
- `case_sensitive_file_extension_comparisons` is selected with the narrow exception below.

`clippy.toml` tightens cognitive complexity from **20 to 15**, function arguments from
**6 to 5**, and function size from **80 to 70** lines. These warnings block the standard
`-D warnings` command. Production helpers have been split at real ownership/policy
boundaries rather than receiving module-wide function-size allowances.

Test setup may fail fast: `allow-unwrap-in-tests` and `allow-expect-in-tests` cover test
functions. Integration-test crates explicitly allow those two lints so shared fixture
helpers can use them too. These attributes live only under `tests/`; they do not weaken
production. A few end-to-end fixtures have documented, function-local size/complexity
exceptions to keep setup and lifecycle assertions together. Debug placeholders remain
forbidden in tests. New exceptions require a narrow scope and a written reason.

## Archive filename case

Registry artifact names and URLs are locked, byte-exact values, not case-insensitive
filesystem lookups. Supported suffixes are lowercase `.conda`, `.tar.bz2`, `.whl`, `.tgz`,
and `.crate`. Basename case is preserved; an uppercase or mixed-case **suffix** is not
silently accepted or normalized. Download names must still match the planned filename
and pass each registry's path validation.

`isolock_core::RegistryArchive::from_filename` centralizes recognition. Its local
`case_sensitive_file_extension_comparisons` allowance records this policy; callers do
not blanket-allow the lint. Unit tests cover all recognized suffixes, uppercase and
mixed-case rejection, query strings, and misleading trailing extensions.

## Coverage reporting scope

`scripts/coverage.sh` instruments the full Cargo workspace with all features and writes
`coverage/lcov.info`. Codecov's `rust` flag covers the entire `crates/` directory, including
core, CAS, planning, proxy, and CLI sources. New crates under that directory are included
without maintaining a second package list. A regression scenario checks the scope against
`Cargo.toml`, rejects stale directories, and verifies the generator/upload configuration.

CI uploads that explicit LCOV file with report discovery disabled. Carryforward is disabled
because each coverage job produces a complete workspace report; missing current data must
not be replaced by an older report. Test source files remain excluded from Codecov's
statistics, not from test execution. Opt-in real-profile integrations still run separately
and their execution is not included in this coverage report.

The shared script and `pixi run coverage` enforce `--fail-under-lines 90`: coverage below
90% fails the job before upload. The existing Codecov project and patch targets remain 90%.
Expanding the old CLI-only flag changes the reporting denominator; compare reports using
the corrected workspace scope rather than interpreting that scope change as a runtime
regression.

CLI fixtures that clear the child environment preserve only `LLVM_PROFILE_FILE` from the
coverage instrumentation. Otherwise the instrumented child's profile is written into its
temporary project and deleted before aggregation, hiding executed CLI paths. Application
configuration remains isolated; no additional source exclusions are used.

## Cargo metadata and supply-chain policy

The CLI uses crates.io `clifacet` 0.10 with default features disabled; optional interactive,
async, MCP, and TUI integrations are not enabled. The lockfile pins both `clifacet` and
`clifacet-macros` to 0.10.0 with their registry checksums. Commands use the documented
`app`/`commands` controller authoring style and declarative groups, not handwritten
request/dispatch plumbing. Version 0.10's controller macros emit optional-feature `cfg`
names in their consuming crate. `crates/isolock/build.rs` registers only those known names
with Rust's `check-cfg`; it enables no Cargo features and keeps unknown-cfg warnings and
strict Clippy active. No vendor patches or optional-feature dependencies are added.

Black-box scenarios cover generated help, usage errors before initialization, nested
global overrides, child argument tails, streams and exit statuses, plus clean-plan
success, CI drift failure, and workstation inspection. Existing profile and proxy suites
exercise the same real binary.

Reviewed-ingestion contracts execute the real binary against local originals, temporary
Git repositories/remotes, and a cold consumer CAS. They check digest mismatches (including
cache hits and duplicate digests), rejected batches, immutable publication records, dirty
checkout preservation, idempotence, concurrent non-force rejection/retry, workflow argv
safety, and conservative ingestion GC roots. The profile path publishes payloads first,
locks to that commit, publishes its manifest, fetches exactly the selected CAS closure,
then removes the originals/remote before offline materialization and execution.

That end-to-end publication scenario uses fixture tools/archives. The separate native
Pixi/Rust integrations remain explicit tests, not evidence of native publication on every
platform. Connected acquisition tests replace the external downloader boundary with a
controlled executable; they do not contact registries. All normal tests remain offline,
and the unchanged coverage gate still includes every workspace crate.

The reviewed developer bundle is `developer-clifacet-0-10`. Run `bash scripts/restore.sh`
to restore it, including the matching Cargo vendor source, before offline validation.
This separate generation preserves the pre-upgrade sandbox for older checkouts. The
publisher watches Cargo manifests and the lockfile as well as Pixi inputs; crate archives
and generated vendor payloads stay on the sandbox transport branch, not the code branch.

First-party packages inherit workspace keywords and the `development-tools::build-utils`
category. Cargo's broad lint group remains an **audit-only** command:

```sh
pixi run --as-is --offline cargo clippy --workspace --all-targets --offline -- -W clippy::cargo
```

Do not combine that audit with `-D warnings` as a replacement for the selected CI policy.
Expected exclusions are optional per-package homepage/documentation metadata and duplicate
transitive crate versions. Review metadata when publishing; this audit is not a license,
advisory, source, or duplicate-version authority.

`cargo deny` and `deny.toml` remain authoritative for those dependency policies. The
existing duplicate-version warning policy and specific advisory exceptions are not
silently turned into Clippy failures or removed by M6. The hermetic CI gate checks bans,
licenses, and sources using restored data. Refresh and review the RustSec database before
running an advisory audit in a network-capable maintenance environment; an offline audit
without a reviewed database is not evidence of current advisory coverage.
