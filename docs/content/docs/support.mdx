## 0.1 support contract

This page is the support contract for Isolock `0.1.0`. An artifact being built or uploaded
is not, by itself, evidence that the corresponding workflow is supported. The table below
separates native CLI artifact coverage from the narrower profile-materialization matrix.

| Surface | 0.1 tested support | Acceptance test | Runner and network | Evidence artifact |
| --- | --- | --- | --- | --- |
| Standalone CLI archive | Linux x86_64 GNU, macOS arm64, Windows x86_64 | Release-artifact smoke job extracts the archive and checks version, help, typed config, and a clean CI plan | Native `ubuntu-latest`, `macos-latest`, `windows-latest`; no registry access | Job status per platform in the CI run |
| Conda CLI package | `linux-64`, `osx-arm64`, and `win-64` packages built by the release workflow | `rattler-build` recipe test invokes the installed package's version, help, and configuration commands | Native matrix runners in the release workflow; offline after build | Job status in the release run |
| Locked-profile runtime materialization | `linux-64`: `rust-pixi` and `rust-standalone` | `tools test profile-materialize` restores the selected reviewed profiles and runs them offline. `rust-pixi` also installs one deterministic Conda fixture with real Pixi after publishing to a disposable Git branch and fetching as a cold consumer; the remote is removed before the offline sync | `ubuntu-latest`, one job per profile; loopback only, no registry | Job status per profile; no uploaded artifact |
| Reviewed storage publication | Linux CI with disposable local Git remotes | Real CLI tests cover ingestion, publication, cold restoration, epoch policy, retries, and producer checkout/index preservation. No test writes to project artifact storage | `ubuntu-latest`; local git remotes, no network | Job status |
| Registry proxy protocols | PyPI, Conda, npm, and Cargo through the `isolock exec` CLI path on Linux | `tools test acceptance` requests each metadata and artifact endpoint from a pinned local snapshot, rejects an unreviewed miss, and checks CAS tampering fails closed | `ubuntu-latest`; loopback proxy against a local CAS | Job status |
| Real package-manager clients | `pixi add` against the generated Conda channel; `cargo add` against the vendored source. Both `linux-64`, offline | `real_pixi_add_resolves_from_the_generated_channel`, `real_pixi_add_reports_a_miss_for_an_unreviewed_package`, `real_cargo_add_adds_a_reviewed_crate_offline`. pip and npm clients are not claimed | `ubuntu-latest` in the profile matrix; loopback and on-disk vendored source | Job status per profile |

Acceptance evidence for these claims is job status in the CI run on the exact commit, plus
the local `tools` invocations named above. CI does not upload a per-claim report artifact;
the release record captures the candidate commit and its run URL instead.

The native artifact smoke check validates that each released standalone CLI can start,
parse commands, validate default configuration, and check an empty legacy plan on its
host. The Conda recipe test checks package installation and CLI startup. These checks do
not assert native profile materialization on macOS or Windows.

## Host and toolchain requirements

- **Standalone CLI:** no Rust or Pixi installation is required to run the CLI itself.
  Source builds require Rust 1.88 or newer (the workspace MSRV). The Windows artifact is
  the x86_64 MSVC executable; Linux support is the x86_64 GNU build, and macOS support is
  arm64.
- **Conda CLI package:** install through a Conda-compatible package manager from the
  `archont561/archont561` Prefix.dev channel. Rust is a build-time requirement, not a
  runtime dependency of the installed CLI.
- **Git storage:** use a Git executable and a configured local path, remote name, or
  credential-free HTTPS source; Git authentication is external to Isolock. Explicit
  connected ingestion requires `curl` and HTTPS access to the already-reviewed source.
- **Profile workflows:** require the reviewed lock/manifests, artifact closure, and declared
  seed/runtime tools. The tested Rust profiles require a Linux x86_64 GNU host and the
  `linux-64` platform. Runtime prefixes must be relocatable and compatible with the host
  distribution's libc/linker. Shell bootstrap requires a POSIX `sh` and a SHA-256 utility
  (`sha256sum` or `shasum`).

## Known exclusions

Isolock does not resolve registry versions, discover transitive dependencies, or provide a
host-network firewall. The proxy acceptance suite verifies the supported HTTP protocol
routes with the CLI and deterministic local fixtures; package-manager client behavior is
covered only by the two real-client journeys named below, and not for pip or npm. Offline
profile materialization is not claimed for macOS or Windows. Git transport may transfer a
broader snapshot before retaining only the selected closure in the local CAS. Automatic
legacy/sharded storage migration, old-epoch deletion, and connected proxy-miss acquisition
are not part of this release contract.

Follow the [release validation checklist](./release-checklist.mdx) for candidate evidence,
non-publishing rehearsal, and the explicit GO/NO-GO process.

## Workflow and trust boundaries

The 0.1 contract uses exact, reviewed inputs. Isolock does not select versions or solve
registry dependency graphs. Planning consumes supported lockfiles and reviewed metadata;
ingestion accepts explicit names, versions, sources, and digests. Connected acquisition is
explicit and pin-verified. Missing proxy artifacts fail closed; a proxy listener is not a
host firewall or a general network sandbox.

The proxy acceptance test exercises real CLI process/environment routing and HTTP protocol
responses against a deterministic local CAS snapshot. Two release-gated journeys in the
profile matrix go further and run real clients: `pixi add` resolves a reviewed Conda package
from the generated channel and fails closed for an unreviewed one, and `cargo add` records a
reviewed crate offline from the vendored source. Both run in CI on `linux-64`.

pip and npm are **not** exercised as clients, and `cargo add` resolves from the vendored
directory source rather than over the proxy. No 0.1 claim covers dependency resolution for
those clients or transitive dependency discovery for any of them.

The profile matrix proves only the selected Rust/Pixi and standalone Rust workflows on
`linux-64`. Other runtime providers, host/target combinations, artifact sizes, and connected
proxy-miss behavior are not covered by this 0.1 support statement. Archived storage epochs
are retained; rollover budgets are not a global remote-size limit, and legacy/sharded
storage conversion is not automatic.

## Install the tested CLI

Use the standalone archive for your host from the [GitHub Releases](https://github.com/Archont561/isolock/releases)
page and verify it against the accompanying `SHA256SUMS`. The release workflow also
publishes Conda packages to the `archont561/archont561` Prefix.dev channel; see that release
for package availability and channel instructions. Building from source with Rust is a
developer route, not a substitute for the installed-artifact acceptance job.

After installation, verify the CLI and local configuration:

```sh
isolock --version
isolock --help
isolock config check
```

Use the [Getting Started guide](./getting-started.mdx) for supported lock/profile inputs,
reviewed ingestion, and offline materialization details.
