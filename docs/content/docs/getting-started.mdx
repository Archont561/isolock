## Installation

For Isolock 0.1, use the standalone archive for one of the tested targets in the
[0.1 support matrix](./support.mdx): Linux x86_64 GNU, macOS arm64, or Windows x86_64.
Download it from [GitHub Releases](https://github.com/Archont561/isolock/releases), verify
`SHA256SUMS`, then extract the archive and place the binary on `PATH`. The Windows archive
contains `isolock.exe`.

The release workflow also publishes Conda packages to the `archont561/archont561`
Prefix.dev channel; availability and exact instructions are listed with each release. A
Cargo source installation is useful for development, but CI's installed-release-artifact
job is the 0.1 support evidence.

## Basic Commands

Verify your installation:

```sh
isolock --version
isolock --help
isolock plan --help
```

Help is generated from the same typed command tree that runs the application. An omitted
command or unrecognized arguments produce diagnostics on stderr and exit status 2, without
loading project configuration. Execution failures use status 1; `exec` preserves the
child's exit status instead. Global options such as `--config` and `--profile` can appear
before or after a subcommand, but options after an `exec` child executable belong to that
child. `bootstrap` remains an alias for profile `sync`.

### 1. Plan Lockfiles

Generate and check dependency airlock plans:

```sh
isolock plan --ci
```

Without a profile/project configuration this checks an existing legacy `.isolock/plan.json`
against the local CAS; it does not discover project dependencies. Use explicit
`--profile NAME --platform PLATFORM` planning for the [locked profile workflow](./profiles.mdx).

### 2. Start the Local Hermetic Proxy

Run the proxy listener in sealed airlock mode:

```sh
isolock serve
```

### 3. Ingest Verified Artifacts

Review `isolock.ingest.json` with exact names, versions, HTTPS sources, filenames, and
SHA-256 pins, then verify the matching local originals. Publication is a separate action:

```sh
isolock ingest --manifest isolock.ingest.json --artifacts originals
isolock push --manifest isolock.ingest.json
```

Neither command resolves a registry. Local ingestion never downloads; the connected workflow
can explicitly use `--download` for reviewed sources. See [reviewed ingestion and publication](./ingestion.mdx)
for the JSON schema, storage limits, two-phase profile publication, and cold-consumer restore.

To set a repository up from scratch, including which files to commit and how a consumer
restores offline, see [adopting Isolock](./adoption.mdx).

### 4. Bootstrap and Activate a Toolchain

After placing the bootstrap script at `.isolock/bootstrap.sh` and provisioning the manifest and CAS blobs, restore the default environment and source its activation script:

```sh
sh .isolock/bootstrap.sh
. .isolock/state/active/activate
```

The manifest at `.isolock/environments/active.manifest` lists one lowercase SHA-256 digest and one archive filename per line. Verified archives must unpack a top-level `bin/` directory. To fetch the storage tree from the origin's `isolock/v1` branch, pass `--remote`.
