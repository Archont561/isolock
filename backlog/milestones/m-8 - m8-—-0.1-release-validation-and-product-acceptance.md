## Purpose

Make the 0.1 release claims match what a clean user can install, configure, and successfully
use. This milestone is a release-confidence/testability slice, not a request to expand the
product into a registry dependency solver. Prior milestones deliver component contracts;
M8 should prove the advertised end-to-end journeys using release-shaped artifacts and an
explicitly supported platform/ecosystem matrix.

## Proposed exit criteria

- [ ] Publish a concise 0.1 support contract: supported host platforms, install artifacts,
  toolchain/runtime requirements, supported workflows, and known exclusions. Do not claim
  a platform or workflow that has not passed its acceptance job.
- [ ] On every platform in that contract, install the built release candidate (not a
  workspace binary), verify version/help/configuration startup, and run a documented
  representative command.
- [ ] For each ecosystem and workflow advertised for 0.1, execute a clean-room CLI
  acceptance journey against deterministic local fixture registries/services: consume
  supported lock/review inputs, acquire through the configured proxy/workflow, verify and
  cache selected bytes, then disable upstream access and prove cold offline restoration/use.
  Capture negative integrity and stale-plan/drift cases as well.
- [ ] Exercise the published-profile and epoch-rollover journeys using disposable remotes
  from a cold consumer, with producer checkout/index invariants and failure/retry behavior
  verified. Reuse the existing real-CLI contracts and identify any missing 0.1 user path.
- [ ] Run the acceptance suite in required CI, make its result a release gate, and rehearse
  the release workflow: install/download each claimed artifact, verify `SHA256SUMS`, and
  retain a concise pass/fail matrix and reproducible release checklist.
- [ ] Make the 0.1 documentation and release notes accurately distinguish tested
  capabilities, optional/fixture-only tests, unsupported behavior, and platform coverage.

## Suggested work breakdown (task IDs unassigned)

1. **Define the 0.1 product contract and support matrix.** Choose the supported operating
   systems, installation routes, ecosystems, and exact claims before adding matrix jobs.
2. **Build clean-room CLI acceptance fixtures.** Drive package-manager/proxy and lock-plan
   journeys through the installed CLI; test online acquisition followed by cold offline
   replay, tamper rejection, drift reporting, and child-process status/arguments where
   those are public 0.1 promises.
3. **Close end-to-end storage/release gaps.** Extend real profile/epoch scenarios only
   where they are part of the chosen 0.1 workflow; smoke-test release artifacts on their
   claimed native runners and perform a release-candidate rehearsal.
4. **Gate and document the release evidence.** Add the required checks to CI, publish the
   support/test matrix and operator checklist, and record a go/no-go review against the
   acceptance criteria.

## Scope boundaries

Keep registry solving/version selection separate unless explicitly added to the 0.1
contract; the current reviewed-manifest and lockfile-driven interfaces remain the product
boundary. Do not require live public registries in routine CI: use hermetic local fixtures,
with any external canary isolated, opt-in, and non-blocking. This milestone does not imply
automatic legacy/sharded storage conversion, archived-epoch retirement, selective network
transport, or native artifact publication to real project storage.
